# QuantGuard Interview QA

## 为什么做这个项目？

为了把模拟账户、历史行情、订单成交和持仓分析形成完整的软件流程，同时训练金融数据建模、后端事务、前端交互和自动化测试能力。

## 当前版本完成了什么？

`v1.0.0` 已完成账户与投资组合、证券管理、历史日线和 K 线、模拟限价订单、执行与取消、成交、持仓收益和回本计算。

## 个人负责什么？

负责前后端架构、monorepo 迁移、数据库和接口、Vue 页面与状态管理、K 线交互、自动化测试、CI 和版本发布。

## 架构如何划分？

后端使用 Controller、Service、Mapper、Entity、DTO 分层；前端使用 API 请求层、Pinia 状态、路由页面、可复用组件和纯计算工具。前后端位于同一 monorepo 中。

## 如何保证交易数据一致性？

订单、现金、成交和持仓变化放在事务中；金额使用 `BigDecimal`；并发更新检查受影响行数或乐观锁；异常时回滚整个流程。

## 为什么删除功能要区分多种情况？

历史行情可以重新生成，订单和持仓等业务数据不能随意级联删除。因此系统区分停用、清空行情和永久删除，并在删除前检查业务引用。

## K 线交互最难的地方是什么？

缩放和拖动会改变可视数据范围，最高价、最低价和右侧收盘价必须跟随可视窗口更新。实现时统一维护可视区间，并用 Playwright 驱动 ECharts 的 dataZoom 行为验证结果。

## 为什么使用 Playwright？

类型检查和单元测试不能覆盖页面切换、localStorage 状态、硬删除确认和图表交互。Playwright 用于验证这些真实浏览器流程，并在 GitHub Actions 中自动运行。

## 如何处理敏感信息？

Tushare Token 通过设置页面提交给本地后端，不写入源码；发布前扫描 `.env`、Token、私钥、日志和构建产物，GitHub Release 只基于通过 CI 的提交。

## 当前不足是什么？

没有实时行情、真实券商、多用户权限和公网部署；当前还需要分别运行前端、后端并配置本地数据库。

## 下一步是什么？

将当前 Web 系统封装为桌面客户端，继续处理后端自动启停、嵌入式数据库、Token 安全存储和 Windows 安装包。
